# ADR-004 — The renderer foundation

**Status:** Accepted
**Date:** 2026-09-17
**Owner:** the author, on `AGENTS.md` §5 and R14 and `Design/TechnicalDesign.md` §6.1, with the owner's assumptions of 2026-09-17

## Context

`AGENTS.md` §5 leaves three things to the first client ADR: the authored resolution, the window style, and whether the scene target is multisampled. R14 admits `d3dx12.h` as the one exception to the no-dependencies rule and asks for its pin. `TechnicalDesign.md` §6.2 asks which shader compiler `FXCompile` drives on the pinned toolset, one of the first things M0 was to find out. The capture path of §6.1 and §10 needs a device with no window from the first frame, because CI is the agent's eyes. And `winrt::com_ptr` brings `winrt::check_hresult` with it, which throws, so the first renderer task (`m0-foundation/T18`) had to decide how a failed `HRESULT` travels. This ADR settles all of it, with the first frame drawn.

## Decision

**The authored resolution is 1920×1080** (`AUTHORED_WIDTH_PIXELS`, `AUTHORED_HEIGHT_PIXELS` in `Client/SceneTarget.h`). Every pass draws at that size, and a pixel font reaches the glass 1:1 there, which is what `GameDesign.md` pillar 3 needs. On a monitor of that size the present is unfiltered; a 4K monitor gets the point-sampled 2×; anything else gets bilinear, letterboxed or pillarboxed (`AGENTS.md` §5; `Client/ScaleMode.h`, `FitAuthored`, a pure function `ClientTests` pins).

**The window is a borderless `WS_POPUP` covering the primary monitor** at its physical pixel size, with the process per-monitor-V2 DPI aware before the window exists, so that a 4K monitor at 150% reports 3840 pixels and not a virtualised 2560. Escape and Alt+F4 close it, handled in the window procedure; DXGI's Alt+Enter toggle is disabled (`DXGI_MWA_NO_ALT_ENTER`). There is no exclusive full-screen mode: the flip-model swap chain over a borderless window is what the compositor presents directly. (`Client/Window.h`.)

**The scene target is 4× multisampled**: an `R8G8B8A8_UNORM` colour target and a `D32_FLOAT` depth buffer at the authored size with four samples each, resolved every frame into a single-sample `R8G8B8A8_UNORM` texture that the present pass samples and the capture reads back. Flat-shaded geometry with hard silhouettes is what multisampling fixes best, and the back buffer cannot be multisampled, which is why the scene target exists (`AGENTS.md` §5). An adapter without four samples for either format gets a single-sample target and a copy in place of the resolve, and the log says so. Resting states are fixed: the colour target in `RENDER_TARGET`, the depth buffer in `DEPTH_WRITE`, the resolved texture in `PIXEL_SHADER_RESOURCE`; whoever transitions one puts it back. (`Client/SceneTarget.h`.)

**The frame loop** (`Client/GraphicsDevice.h`) is one direct command queue, one command list, `FRAMES_IN_FLIGHT` = 3 command allocators, and one fence whose value per frame slot is what `BeginFrame` waits for before reusing the slot's allocator; `EndFrame` closes, executes and signals. The swap chain (`Client/SwapChain.h`) is flip-discard, three buffers at the client size, `DXGI_SCALING_NONE`, presented with vertical synchronisation. Descriptor heaps are managed by hand as a fixed capacity handed out in order and never returned (`Client/DescriptorHeap.h`), which is all seven fixed pipelines need.

**The `HRESULT` policy.** Every `HRESULT` in `Client` goes through `winrt::check_hresult`, and every Win32 `BOOL` that can fail through `winrt::check_bool`; nothing in `Client` reports a failure by return value. The exception, `winrt::hresult_error`, is caught once, in `App::Run`, logged with its code and message, and fatal: the process exits 1. Device removal is fatal too, until the ADR that adds recovery supersedes this point. A destructor never throws: `GraphicsDevice`'s final wait is caught and logged. The executable links `runtimeobject.lib` for `RoOriginateLanguageException`, which `hresult_error`'s constructor calls, beside `d3d12.lib` and `dxgi.lib`.

**The debug layer** is enabled in Debug builds when the SDK layers are installed; when they are not, `D3D12GetDebugInterface` fails with `DXGI_ERROR_SDK_COMPONENT_MISSING` (0x887A002D), the device runs unvalidated, and the log says so, so that a clean capture on such a machine is not mistaken for a validated one. Its queue is drained into the log every frame; warnings and worse are counted, and the count decides the capture's exit code.

**The capture** (`--capture <frames> <directory>`) creates no window and no swap chain: the scene target is drawn `<frames>` times, `frame-<n>.bmp` is written for every hundredth frame from n = 0 through `Core`'s `WriteBitmap`, and `<directory>\capture.log` records the adapter, the debug-layer state and every message. Exit codes: 0 clean, 2 when the debug layer reported anything, 1 for a bad command line, a failed `HRESULT` or a frame that could not be written. The design's `--capture <match> <ticks> <directory>` form (`TechnicalDesign.md` §6.1) arrives with the scripted match (`m1-vertical-slice/G2`); the frame count stands in for the ticks until then. `--warp` selects the software rasteriser on either path. The windowed path logs to `Logs\Client.log` under the user directory (§9).

**`d3dx12.h` is DirectX-Headers v1.606.3**, the file `include/directx/d3dx12.h` of that release, vendored whole as `Client/d3dx12.h` with the release's MIT licence beside it as `Client/d3dx12.LICENSE.txt`. Its SHA-256 as published is `aa62cf18f3e34848c3a020ba3c8583a4e056fb0e03da3f915e3992db39dc17cb`; the checkout renders it with CRLF like every source (`.gitattributes`), at which it hashes to `074358ff59a78f119cd89dab5f896cc0401dcc7881b70ab9fad279f06dbcce44`. It is compiled with `D3DX12_NO_STATE_OBJECT_HELPERS`, because the state-object helpers are the one part that includes WRL's `ComPtr`, which R14 excludes, and `D3DX12_NO_CHECK_FEATURE_SUPPORT_CLASS`, the part that tracks the newest SDK; neither is used. Nothing else outside the SDK: `winrt::com_ptr` and `winrt::check_hresult` come from the SDK's `winrt/base.h`. A newer release replaces the file whole and a superseding ADR records its version and hash.

**Shaders are shader model 6.0 through `FXCompile`**, which drives the SDK's `dxc` itself when the model is 6.x (Visual Studio documents this and the build proves it, below). Each `.hlsl` under `Client/Shaders/` compiles to one header under `Client/CompiledShaders/`, declaring `g_<Shader>`, which the pass that binds the pipeline includes and nothing else does (`AGENTS.md` §2). Neither `dxc` nor `fxc` creates the directory its `/Fh` names, so `Client.vcxproj` makes it in a target after `PrepareForBuild`. Every shader compiles with debug information embedded in its container (`/Zi` and `-Qembed_debug`) in both configurations: the toolset would pass `/Zi` in Debug alone, `dxc` warns when `/Zi` has no PDB path, CI's `/warnaserror` makes that warning fatal, and a shader step that differs between the configurations is what `AGENTS.md` §3 rules out; the cost is a few kilobytes of PDB per shader in the executable. The fallback the design allowed, 5.1 through `fxc`, was not needed.

## Consequences

- Every layout, glyph and integer position in the interface is authored at 1920×1080 and unconditional; the one place that reads the window's size is `FitAuthored`. A 2560×1440 monitor, the common one after 1080p and 4K, gets the bilinear path and its text is the softest of the three; the 1:1 and 2× paths are the ones worth keeping common.
- Four samples cost memory and bandwidth: the colour target is 33 MB and the depth buffer 33 MB at 1080p (1920 × 1080 × 4 bytes × 4 samples each), plus the 8 MB resolved texture, and a resolve every frame. A lighter scene target reopens this ADR with a frame to compare.
- There is no exclusive full-screen mode and no display-mode change; the game runs at the desktop's resolution and scales. Multi-monitor placement is the primary monitor, and a preference to choose another is the preferences ADR's.
- Nothing in `Client` has an error return, so nothing above it checks one; the cost is that a failed `HRESULT` anywhere ends the process, until device-removed recovery exists.
- A capture without the SDK layers cannot fail on a debug-layer message; the log records which kind of capture it was, and the owner's run (`m0-foundation/T22`) is the validated one until CI's runner has the layers.
- `d3dx12.h` is pinned by hash: a byte changed in it is a decision, and a grep for `ComPtr`, `AddRef(` or `Release(` over `Client` is read excluding the vendored file, which mentions all three in the parts that are compiled out.
- The shader step depends on the toolset's `FXCompile` driving `dxc` for 6.x; a toolset that stopped doing so would fail the build at the first shader rather than silently compile 5.1.

## Measurements

- **`FXCompile` drives `dxc` for shader model 6.0 on the pinned toolset**: CI's Windows job (`.github/workflows/build.yml`, the run this ADR lands in) built `PresentVS.hlsl` and `PresentPS.hlsl` with `ShaderModel` 6.0 from a clean checkout on the `windows-latest` image, and `fxc` cannot compile a 6.x target, so a green build with that setting is the evidence. The run number and the toolset it printed are in `tasks/Archive/m0-foundation.yaml`, T18's notes.
- **The vendored header's hashes** were computed with `sha256sum` over `Client/d3dx12.h` in the checkout (CRLF) and over the same bytes with the carriage returns removed (the release's LF form).
- **The scene target's memory** is arithmetic on the formats above, not a measurement.
- **WARP on the CI runner**: the first capture job (`m0-foundation/T21`, CI run 35) reported `Microsoft Basic Render Driver (WARP), debug layer on` and a scene target of four samples on the `windows-latest` image, so the runner has both the software rasteriser and the SDK layers, and a debug-layer message there fails the job as §10 asks; three hundred frames at 1920×1080 took 3.7 seconds. The capture log is printed in every run's job log.
